# Статья (Habr): план

Рабочее название: **«DHCP, который не падает: Kea в режиме hot-standby»**

Угол: не «как установить Kea», а «что на самом деле происходит с арендами, когда
падает первичный сервер» — и почему общая база лизов сама по себе не является
отказоустойчивостью. Это ровно то заблуждение, на котором люди обжигаются.

## Структура

1. **Постановка.** DHCP как сервис, от которого зависит доступность всей сети,
   но о котором вспоминают последним. Почему «поставим второй сервер» — не ответ.
2. **Общая БД ≠ HA.** Разбор заблуждения: два сервера с одной базой всё ещё
   раздают конфликтующие адреса, если не договорились между собой.
3. **Режимы Kea HA.** hot-standby против load-balancing: когда какой и почему
   для кампусной сети чаще нужен первый.
4. **Стенд.** Топология, docker compose, конфиги. Ссылка на репозиторий.
5. **Ломаем.** Гасим primary, смотрим на heartbeat, max-unacked-clients,
   переход standby в partner-down. Что видит клиент.
6. **Грабли.** ← самое ценное. Всё, на чём споткнулся при сборке стенда:
   control agent против выделенного HA-листенера, инициализация схемы БД,
   пути к hook-библиотекам.
7. **Что дальше.** Куда это масштабируется в реальной сети.

## Правила

- Ноль материала с работы. Всё воспроизводится на этом стенде с нуля.
- Репозиторий — на английском, статья — на русском. Один труд, два рынка.
- Скриншоты только со своего стенда.
